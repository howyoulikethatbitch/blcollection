# 💠 Azure BL Collection

## Master Specification v1.0 — Initial Main Web App

### 1. Project Purpose

**Azure BL Collection** is a personal, browser-based library and launch hub for a collection of independently hosted **BL visual novels**.

The Collection itself is **not a visual novel player**.

Instead, it provides an attractive library where each novel has its own separate web application.

```text
                 AZURE BL COLLECTION
                    GitHub Pages
                         │
             ┌───────────┼───────────┐
             │           │           │
           READ        READ        READ
             │           │           │
             ▼           ▼           ▼
          BL VN #1    BL VN #2    BL VN #3
             │           │           │
       GitHub Pages GitHub Pages GitHub Pages
```

Each individual VN will be developed separately in the future.

# 5. Pixel-Art Usage

The style should be **moderate**, not overwhelming.

Pixel art should appear throughout:

* decorative elements
* icons
* buttons
* headings
* cards
* borders
* backgrounds
* small animations
* petals
* stars
* UI accents

### Pixelated typography

Yes.

Pixel-style fonts should be used especially for:

* Logo/title treatments
* Section headings
* Buttons
* Labels
* Decorative text
* Novel titles where appropriate

However, long descriptions and other reading-heavy UI should prioritize readability.

So we'll use a **pixel + readable font pairing** rather than forcing every paragraph into a pixel font.

# 8. Featured System

Featured novels are **manually designated**.

Each novel's data can eventually contain something equivalent to:

```text
featured: true
```

or

```text
featured: false
```

This means you control exactly which stories appear in Featured.

No algorithm is necessary.

---

# 9. Long & Short Collections

These are strict collection rules.

### 🌙 Long BL Novels

**Exactly 12 chapters**

Designed as longer reading experiences.

### 🌸 Short BL Novels

**Exactly 8 chapters**

Designed as one-sitting/shorter experiences.

The collection should clearly communicate this distinction.

# 14. Content Rating

The collection will support content ratings because different VNs may have different themes.

The important global rule is:

> **No explicit sexual content.**

The rating system is primarily for communicating thematic intensity, such as:

* mature emotional themes
* violence
* death
* psychological themes
* darker subject matter

We'll keep the exact labels flexible until we finalize the content taxonomy.

---

# 15. Read Button

This is an especially important architectural requirement.

The Collection does **not** embed the VN.

Instead:

```text
[ READ ]
    ↓
opens the VN's separate GitHub Pages website
```

The VN should open in a **new browser tab**.

This leaves Azure BL Collection available in the original tab.

---

# 16. Placeholder System

Because the collection will initially have no real VNs, the site should support beautiful placeholder entries.

Example:

```text
┌─────────────────────┐
│                     │
│     🌸 COMING SOON  │
│                     │
│  A new story is     │
│  waiting to bloom.  │
│                     │
└─────────────────────┘
```

The user also wants the ability to eventually add/change cover artwork conveniently.

### Important implementation principle

We should **not pretend that a browser upload permanently modifies GitHub Pages**.

For MVP, we'll design the data/assets system so covers can be added to the repository cleanly.

A future content-management/upload workflow can be added if desired.

# 23. Animation

Moderate animation.

Possible effects:

* Floating petals
* Subtle star twinkles
* Card hover animations
* Button interactions
* Gentle page transitions
* Pixel-art decorative motion

Avoid:

* excessive motion

# 24. Audio

**No audio for Azure BL Collection MVP.**

# 25. Content Data Architecture

This is one of the most important technical decisions.

We'll use a **data-driven collection**, rather than hardcoding individual novels into every page.

Conceptually:

```text
src/
│
├── data/
│   └── novels.json
│
├── assets/
│   ├── logo/
│   ├── banners/
│   ├── covers/
│   ├── icons/
│   └── decorations/
│
├── pages/
│
└── components/
```

The exact technology/file structure will be determined by Replit during implementation, but the principle is:

> **Novel information should live in structured data, not be scattered throughout the UI code.**

So adding Novel #10 shouldn't require manually rebuilding the Home page.

# 27. Scalability

The MVP should comfortably support the future transition from:

```text
3 novels
```

to:

```text
10 novels
```

to:

```text
30+ novels
```

without requiring a fundamental redesign.

However, we're **not** building a complicated database/backend just because it might be useful someday.

The principle is:

> **Simple now, scalable where it matters.**

# 29. Most important architecture rule

I'm going to make this a permanent project rule:

> ### **Azure BL Collection and individual BL visual novels are separate projects.**

The Collection is the **library/launcher**.

The VNs are **independent web applications**.

For example:

```text
GitHub
│
├── azure-bl-collection
│
├── vn-moonlit-garden
│
├── vn-summer-rain
│
├── vn-blue-hour
│
└── vn-untitled
```

Each can have its own GitHub Pages deployment.
